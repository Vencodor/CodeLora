# 프로젝트 지식을 학습하는 LoRA + RAG

2026-10-27 · Meta AI 해커톤 개인 참가 프로젝트 메모

## 1. 목표와 구조
프로젝트 문서·코드를 합성 데이터로 확장하고 Muse Glimmer에 프로젝트별 LoRA를 학습해 별도 어댑터로 저장한 뒤, 추론 시 적용해 RAG와 함께 사용한다. 일반 RAG보다 도메인 지식과 제약을 잘 적용할 수 있는지 검증하며 성능 향상은 보장하지 않는다. 향후 서버는 합성·학습·저장·서빙을, 클라이언트는 비교와 실제 사용 데모를 담당한다.

## 2. 데모 방향
프로젝트 고유 규칙과 설계 제약을 아는 변경 리뷰어를 지향한다. 단순 지식 QA 정답률을 넘어 새로운 변경에 중요한 제약을 적용하는 가치를 보여주되, 자료에 없는 설계 의도를 만들지 않는다. 리뷰 기능은 아직 구현하지 않았다.

## 3. 우선 구현 범위
먼저 로컬 파일 입력부터 합성 데이터 저장까지 구현하고, 이후 서버측 파일 수신기를 연결한다. LoRA 학습·RAG·서빙·리뷰 기능은 다음 단계이며, 별도 코딩 세션의 실제 진행 상태나 완료 여부는 이 메모에서 추정하지 않는다.

## 4. 합성 흐름
Muse Spark 1.3 Contributor를 교사로 사용한다. 원문 읽기·정리와 출처/버전 보존 → 의미 단위 분할 및 필요한 문맥 제공 → 원문 기반의 다양한 QA와 질문 중심 설명문 생성 → 형식·빈 출력·완전 중복 확인 및 원문 대조 표본 검토 → 원시 JSONL과 학습용 변환 결과 저장 순서다.
SPA의 직접 생성과 SMT/Focal Rewriting의 질문 중심 다양화를 참고한 변형이며 논문 전체 재현은 아니다. 별도 근거 카드, 전수 LLM 사실 검증, 자동 RAG 실패 재합성, 검색 쿼리 학습은 기본 범위에서 제외한다.

## 5. 학생이 배우는 방식
교사는 원문을 보지만 학생은 원문 전문이나 답을 담은 코드 본문 없이 질문/지시를 보고 답변을 학습한다. 프로젝트·파일·함수·조건을 명확히 해 질문이 독립적으로 이해되게 한다.
QA/설명문 비율과 최종 학습 형식은 조정 가능하며, 1:1 비율이나 모든 설명문의 SFT 변환을 검증된 최적값으로 보지 않는다. 원시 출력은 보존하고, 향후 리뷰 입력 diff는 검토 대상이므로 지금의 지식 기억 예제와 구분한다.

## 6. 품질과 운영
근거가 부족하면 이유를 남기고 정상 결과 0개를 허용하며 오류와 구분한다. 저장 완료 결과는 재사용하되 전송 후 결과가 불명확한 작업은 별도 처리하며, 중복 과금 방지를 완전히 보장하지 않는다. 출처·입력 스냅샷·설정을 추적한다.

## 7. 데이터 전송 원칙
Contributor에 전송한 데이터는 제공자 모델 학습에 쓰일 수 있으므로 비밀정보와 전송 불가 파일을 제외한다. 실제 외부 전송·유료 API 실행은 별도 확인 후 진행하며, 합성 품질 검증과 API 동작 검증은 구분한다.

## 8. 비교와 평가
같은 기본 Glimmer의 RAG-only와 LoRA+RAG를 비교한다. 각 모델이 검색 쿼리를 생성하며, 동일 검색 도구·설정·데이터 접근 조건에서 전체 흐름을 비교하되 쿼리와 검색 결과 자체는 달라질 수 있다. 필요하면 동일 검색 문맥을 주는 비교로 생성기 효과를 분리한다.
평가 질문·정답·리뷰 주석은 합성 및 학습 입력에서 제외하지만, 평가하는 지식의 원문은 학습할 수 있다. 변형 QA의 무작위 분할만으로 일반화를 주장하지 않고, 지식 기억과 새로운 diff에 대한 규칙 적용을 구분해 성능·환각·비용·지연의 실제 결과를 정직하게 보고한다.
